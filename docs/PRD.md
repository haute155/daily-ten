## 1. 제품 개요

### 1.1 한 줄 정의

**Daily Ten**은 사용자가 매일의 행동을 10점 만점 점수로 기록하고, 그 점수 체계 자체를 직접 설계·버전 관리·개선해 나가는 자기관리 플랫폼이다.

### 1.2 문제 정의

기존 체크리스트/습관 앱의 한계:

- "했다/안 했다"의 완료 기록에만 집중해 금방 형식적이 된다.
- 평가 기준(어떤 항목을, 어떤 비중으로)을 바꾸고 싶어도 그 변경이 기록과 연결되지 않는다.
- 자기 생활 시스템을 실험하고 개선한 **흔적**이 남지 않는다.
- 기록은 쌓이지만 통찰로 이어지지 않는다.

### 1.3 해결 접근

이 제품은 단순 기록 도구가 아니라 **자기 시스템 실험 도구**다. 다음 루프를 소프트웨어로 지원한다.

```
시스템 설계 → 실행 → 기록 → 분석 → 개선 → 재설계
```

핵심 차별점은 "점수"가 아니라 **점수 체계의 진화 이력**이다. 사용자는 다음과 같은 통찰을 얻을 수 있어야 한다.

- "운동 가중치를 올렸더니 평균이 떨어졌네"
- "독서를 빼니까 점수가 안정되네"
- "야근 있는 날은 평균 -2점이네"

## 2. 제품 철학

기능 우선순위와 UX 판단의 기준이 되는 원칙:

1. **Win small, win daily** — 매일의 작은 승리를 취한다.
2. **의지보다 시스템** — 흔들리는 의지 대신 설계된 구조에 기댄다.
3. **기억보다 기록** — 흐려지는 기억 대신 남는 기록에 기댄다.
4. **점수는 내가 설계한다** — 평가 기준의 주인은 사용자다.
5. **설계는 계속 진화한다** — 버전 이력이 곧 성장의 기록이다.

이 철학에서 도출되는 제품 판단 기준:

- 기능이 "빠른 기록"을 방해하면 그 기능이 진다.
- 설계 변경은 아무리 작아도(순서, 가중치) 이력으로 남는다.
- 통계는 "잘했다/못했다"가 아니라 "시스템을 어떻게 고칠까"를 묻게 만들어야 한다.

## 3. 타겟 사용자

### 주 사용자

- 제작자 본인 (1차 검증 대상)
- 자기관리를 원하지만 복잡한 앱은 오래 못 쓰는 사람
- 단순 투두보다 "어떤 기준으로 살 것인가"에 관심 있는 사람

### 사용자 특성

- 빠른 기록 선호 — 앱을 열면 바로 행동할 수 있어야 함
- 과한 기능보다 구조적이고 명확한 도구 선호
- 모바일 사용 비중이 높음

## 4. 핵심 사용자 시나리오

### S1. 첫 사용 (온보딩)

1. 앱 진입 → 철학과 사용 방식을 짧게 확인
2. 체크리스트 항목과 가중치 설정 (총합 10점)
3. 오늘 점수 첫 기록
4. "이 시스템을 계속 개선할 수 있다"는 인상을 받고 종료

### S2. 일상 사용 (핵심 루프, 목표 10초)

1. 앱 진입 → 오늘 체크리스트가 바로 보임
2. 항목 탭 → 총점 실시간 계산
3. (선택) 짧은 메모
4. 저장 → 인사이트 문구 확인 (🔥 3일 연속 7점 이상!)

### S3. 시스템 재설계

1. 설정 페이지에서 항목 이름/순서/가중치 수정
2. 저장 시 새 버전 생성 + 변경 요약(diff) 표시
3. 오늘 이미 기록했다면 "변경사항은 내일부터 적용" 안내
4. 이후 통계에서 변경 전후 평균 비교

### S4. 회고

1. 히스토리 캘린더에서 점수 흐름 확인 (기준 점수 기반 색상)
2. 특정 날짜 → 당시 기록·메모·적용 버전 확인
3. 통계 페이지에서 평균/추세/항목별 기여도/버전 전후 비교

## 5. 도메인 규칙

### 5.1 점수 규칙

- 하루 총점은 **10점 만점**. 항목 가중치 총합이 10이 되도록 설계를 유도·검증한다.
- MVP에서 항목은 boolean 체크형. 정량형(물 2L, 독서 30분)은 확장 가능하게 열어둔다.
- 점수 = 체크된 활성 항목들의 weight 합.

### 5.2 기록 규칙

- 하루에 기록은 1개. 같은 날 재진입 시 수정 가능.
- 메모는 선택 사항.
- 과거 날짜 기록은 수정은 물론 **소급 입력**("지금이라도 입력하기")도 가능하다. 등록·수정 시 원하는 레시피 버전을 직접 선택할 수 있다. 단 UX상 당일보다 한 단계 더 번거롭게 설계한다(당일 기록 유도).

### 5.3 버전 규칙

- 체크리스트 구성은 버전 단위로 관리한다.
- 새 버전 생성 트리거: 항목 **추가 / 삭제 / 이름 변경 / 순서 변경 / 가중치 변경 / 카테고리 변경** (작은 수정도 전부).
- 오늘 이미 기록한 상태라면 변경은 **내일부터 적용**된다.
- **draft 흡수**: 아직 발효되지 않은 버전(연결 기록 0개 + 적용 시작일이 오늘 이후)을 다시 수정하면 새 버전을 만들지 않고 그 버전을 덮어쓴다. "버전 = 실제로 살아본 구성" — 적용 전에는 몇 번을 고쳐도 버전이 늘지 않는다. UI는 이런 버전에 "사용 대기" 뱃지와 적용일 안내를 보여준다.
- 과거 기록은 당시 적용된 버전 기준으로 유지된다 (기록-버전 연결 불변). 기록이 붙은 버전은 불변이다.
- 버전 간 diff(무엇이 어떻게 바뀌었는지)를 사람이 읽을 수 있는 문장으로 보여준다.
- 통계의 버전 비교에는 기록이 1개 이상 붙은 버전만 노출한다.

### 5.4 분석 규칙

- 기본 제공: 평균 / 최고 / 최저 / 추세, streak(연속 기록, 연속 고득점)
- 버전 변경 전후 평균 비교가 가능해야 한다.
- 항목별 체크율·기여도를 보여준다.
- 인사이트 문구는 mock 계산이라도 실제 데이터 기반으로 생성한다. 과장 없이 짧고 명확하게.

## 6. 기능 명세 (페이지별)

우선순위: **P0** 핵심(없으면 제품이 아님) / **P1** 중요 / **P2** placeholder 허용

### 6.1 오늘 기록 `/today` — P0

앱의 심장. UX 목표: **10초 내 체크 완료**.

- 오늘 날짜, 현재 적용 버전 표시
- 체크 항목 목록(항목별 점수 표시), 총점 실시간 계산
- 메모 입력
- **자동 저장** — 저장 버튼 없음. 체크/메모 변경 시 디바운스 후 자동 저장, 상태는 "자동 저장됨" 인디케이터로 표시. 페이지 이탈·새로고침 직전 변경도 유실 없이 전송
- 인사이트 문구 배너

### 6.2 체크리스트 설정 `/settings` — P0

- 현재 활성 버전 정보 + "이 구성은 YYYY.MM.DD부터 적용 중" 문구
- 항목 카드 UI: 이름/가중치 수정, 추가/삭제, 순서 변경
- 총합 10점 검증 UI (10점이 아니면 저장 불가 또는 명확한 경고)
- 저장 시 새 버전 생성 + 변경 요약 표시
- 오늘 기록 완료 시: "오늘 점수는 이미 체크하셨어요. 변경사항은 내일부터 적용됩니다"

### 6.3 히스토리 `/history` — P0

- 월 단위 캘린더, 날짜별 점수 표시
- **사용자 설정 기준 점수** 기반 색상 구분 (기준 미만/이상; 색상만으로 구분하지 않고 보조 표시 병행)
- 기록/미기록 구분, 버전 변경 발생일 표시(뱃지/아이콘)
- 날짜 클릭 → 상세 페이지

### 6.4 날짜별 상세/수정 `/history/[date]` — P1

- 해당 날짜, 당시 적용 버전 정보, 체크 상태, 점수, 메모
- 수정 저장 (당일 기록보다 진입 단계가 하나 더 깊음)
- "가급적 당일 기록을 권장합니다" 류의 안내

### 6.5 통계 `/stats` — P1

- 평균 / 최고 / 최저, 주간·월간 추세 그래프
- streak (연속 기록, 최장 기록)
- 항목별 체크율, 항목별 점수 기여도
- **버전 변경 전후 평균 비교** (버전별 사용 기간·평균·최고점)
- 최근 7일 평균 vs 이전 7일 평균

### 6.6 온보딩/철학 `/onboarding` — P1

- 한 줄 소개, 핵심 철학 3~5개, 시작하기 CTA. 짧게.
- 첫 진입 시 1회 노출 + 이후 메뉴에서 접근 가능

### 6.7 Placeholder — P2 (이번 범위에서 실구현 금지)

- AI 항목/가중치 추천: 버튼 → mock 추천 카드
- 친구 공유: 공유 카드 UI(최근 7일 평균, streak 배지) + "공유 링크 생성 예정"
- 로그인/회원가입, 푸시 알림, 서버 저장, 결제, 커뮤니티, 실시간 동기화: 전부 제외

## 7. 데이터 모델

버전과 날짜별 기록이 명확히 분리되는 구조를 유지한다. (실제 타입: `src/lib/types.ts`)

- **ChecklistItem** — id, label, weight, order, isActive, category?(기본 6종 키 또는 커스텀 카테고리 id, 미지정=미분류), createdAt, updatedAt
- **CustomCategory** — id, label. 사용자가 직접 추가한 분류 (기본 6종은 코드 상수). 삭제 시 해당 항목들은 미분류로 표시
- **ChecklistVersion** — id, versionNumber, title, items[], totalScore, changeSummary, effectiveFrom, effectiveTo(null=현재), createdAt
- **DailyEntry** — id, date(YYYY-MM-DD), checklistVersionId, checkedItemIds[], score, note, createdAt, updatedAt
- **VersionDiff** — versionId, previousVersionId, changes[] (type: add | remove | rename | reorder | weight-change, before/after, description)
- **InsightSummary** — currentStreak, highScoreStreak, weeklyAverage, monthlyAverage, averageTrend(up|down|flat), monthlyImprovement

핵심 불변식:

1. `DailyEntry.score`는 항상 해당 `checklistVersionId` 버전 기준으로 계산된 값이다.
2. 버전은 수정하지 않고 새로 만든다(append-only). 기존 버전은 `effectiveTo`로 닫는다.
3. 활성 버전의 items weight 총합은 10이다.

## 8. 상태 / 예외 상황

UI가 깨지지 않아야 하는 상태 목록:

- 체크리스트가 하나도 없음 (첫 사용)
- 오늘 기록 없음 / 오늘 기록 완료됨
- 가중치 총합 ≠ 10 (설정 중)
- 히스토리·통계 데이터 없음 또는 부족 (사용 초기)
- 버전은 존재하나 연결된 기록이 거의 없음
- 과거 날짜 기록이 비어 있음
- localStorage 미하이드레이션 상태 (SSR 첫 렌더)

## 9. UX 원칙

- **모바일 퍼스트**, 한 손 조작, 충분한 터치 영역
- 오늘 기록 10초 내 완료 — 불필요한 모달·단계 금지
- 기록은 빠르게, 분석은 깊게
- 당일 기록은 쉽게, 과거 수정은 의도적으로 한 단계 더 깊게
- 색상만으로 상태를 구분하지 않기 (접근성)
- 디자인 톤: 카드 기반, 담백하고 정교하게. 자기계발 앱 특유의 과한 감성 배제. 동기부여 문구는 짧고 가볍게

## 10. 비기능 요구사항

## 11. 성공 기준

- 오늘 기록이 실제로 10초 안팎에 가능하다
- 버전 관리 개념이 사용자에게 명확하게 보인다
- 버전 변경 전후 평균 비교가 가능하다
- 제작자가 최소 2주 이상 실사용할 수 있다
- 단순 기록이 아니라 **개선 욕구를 만드는** 통계가 있다
- "이 앱은 내 생활 시스템을 설계하는 도구다"라는 느낌이 산다
